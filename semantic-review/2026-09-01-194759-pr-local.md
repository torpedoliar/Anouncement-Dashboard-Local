# Adaptive Login Profile hardening: bound profile versus live credential relay

Diff ini memperbaiki temuan pass sebelumnya pada redaksi discovery evidence, profile `STALE/PENDING` ketika revalidasi menemukan target reachable tanpa kandidat, serialisasi summary list/detail, outcome JSON 401/403, dan optimistic CAS pada lifecycle profile. Snapshot profile sekarang kanonis dan mencakup entry/final/action path, mode, method, field, serta kontrak API; tetapi route relay POST belum membandingkan snapshot live itu sebelum secret dibuka. Hasil verifikasi juga masih dapat menulis status aplikasi/profile dari request uji yang tidak sepenuhnya sama dengan binding, dan satu jalur error memasukkan text request mentah kembali ke profile. **Watch for: P0 (confirmed)** credential relay POST dapat mengirim password ke form action/redirect yang sudah berubah dari fingerprint approved; **P1 (confirmed)** ada race check-to-decrypt di semua jalur credential dan persistence verification tidak selalu authoritative.

**Verdict**: NEEDS_CHANGES

## High-level view

**Confirmed:** boundary discovery kini menyimpan origin/pathname dan kategori struktural, bukan query, cookie, token, atau prose detector mentah. Revalidasi yang selesai normal tanpa form/kontrak mengubah profile menjadi `PENDING` + `STALE`, sedangkan kegagalan observasi tetap retryable.

**Confirmed:** fingerprint v2 memuat routing semantic dan relation profile daftar/detail melewati serializer yang sama. Guard peluncuran masih hanya membandingkan `PortalApp` dengan row profile yang sudah dibaca; ia tidak membuktikan `finalUrl` dan `formAction` hasil fetch runtime masih fingerprint yang disetujui, sementara POST relay memilih action runtime itu.

**Confirmed:** 2xx JSON menjadi `TRANSPORT_VALIDATED` dan 401/403 menjadi `REJECTED`, bukan `CREDENTIAL_ACCEPTED`. Setelah dispatch, outcome profile memeriksa subset konfigurasi dan outcome `PortalApp` tetap ditulis saat subset itu tidak cocok; pesan dispatch mentah juga dapat masuk ke profile.

**Confirmed:** CAS/retry melindungi discovery, approval, stale transition, dan verification write. Boundary credential release tidak memakai conditional read atau reservation yang setara, sehingga perubahan profile tepat setelah guard masih dapat diloloskan oleh snapshot memori lama.

<summary>Issues (6)</summary>

1. **P0 — Live POST relay bypasses the approved route fingerprint (confirmed)** — `app/api/sso/post/route.ts:102-105` validates only the persisted relation, decrypts at `:131`, then derives a fresh `actionUrl` from runtime HTML at `:166-169` and posts it at `:183-189`. Fetch/detect the live route before credential lookup, compare its canonical snapshot—including final/action origin/path—to `loginProfileFingerprint`, CAS-mark it stale on mismatch/no candidate, and abort before decrypting.
2. **P1 — Credential release has a check-to-decrypt race (confirmed)** — page, POST relay, and REROUTE relay each validate an already-loaded profile before separately reading/decrypting credentials (`app/portal/app/[appSlug]/page.tsx:152-155,209`; `app/api/sso/post/route.ts:102-105,131`; `app/api/sso/reroute/route.ts:55-58,90`). Add one conditional profile authorization/reservation immediately before the credential read, keyed by approved/current/bound fingerprint and profile version, so a concurrent stale transition invalidates the release.
3. **P1 — Verification outcome can describe a configuration that was never bound (confirmed)** — `app/api/portal-apps/verify-login/route.ts:95-109` compares only target path, mode, method, and two field names; it ignores extra-field names and selected API contract, while `:112-121` always writes the app verification fields. Persist profile or app outcome only after a canonical saved-config/profile-binding comparison; otherwise retain the result in audit/UI only.
4. **P1 — Rejected verification persists request-derived query metadata in `lastError` (confirmed)** — a missing JSON contract interpolates `jsonApi.path` and probe prose at `app/api/portal-apps/verify-login/route.ts:246-253`; that message is passed to the profile writer and stored verbatim (apart from length) at `lib/portal-login-profile.ts:779-782`. Replace persisted error strings with a fixed safe reason code/message, never relay/probe text or submitted paths.
5. **P1 — Frequent health drift detection still hashes a partial route (confirmed)** — `lib/portal-health.ts:77-87` and app create/update fingerprint calls omit `finalPath`, `formActionPath`, and API contracts even though `login-route/v2` supports them. Build the health snapshot from the fetched final URL/form action (and profile contracts where applicable), or use the bound profile fingerprint directly so action/API drift is not displayed as unchanged for the revalidation interval.
6. **P2 — Trust-boundary regressions are untested (confirmed)** — `scripts/test-fingerprint.ts` verifies the pure hash, but no test covers live-action mismatch blocking, conditional launch authorization, non-authoritative verification writes, or safe `lastError` persistence. Add focused tests around these public transitions before treating the profile as a credential-release control.

<summary>Details</summary>

### The POST relay trusts an old profile and then follows a new credential target

**Confirmed:** `buildLoginProfileCandidate()` records `finalPath` and `formActionPath` and includes them in the v2 fingerprint (`lib/portal-login-profile.ts:409-467`). `profileMatchesConfiguration()` checks only configured origin, entry/final path, mode, method, username field, and password field (`:666-676`); `assertPortalAppProfileLaunchEligible()` applies that persisted comparison at `:717-733`. No operation in `app/api/sso/post/route.ts` derives a live fingerprint before the credential boundary.

```
approved profile fingerprint ──> persisted guard ──> decrypt credential
                                      │
                                      │ does not compare
                                      ▼
live fetch ──> finalUrl + formAction ──> actionUrl ──> relay POST
```

**Confirmed:** `fetchLoginPage()` follows redirect locations and POST resolves `fresh.formAction` against the final runtime URL. A target whose redirect or form action changes after approval can receive the credential through a route absent from the approved fingerprint; background revalidation is due only on its cadence. Prefetch and detect without a credential, require the same canonical snapshot used by discovery to equal the app's bound fingerprint, and atomically mark/block on no candidate or drift before querying `PortalUserAppCredential`.

**Confirmed:** health is not a compensating control. `lib/portal-health.ts:77-87` calls `computeLoginFingerprint()` with entry URL, mode/method, fields, and extra names, but not fetched final URL/action. `app/api/portal-apps/route.ts:131-140` and `[id]/route.ts:133-142` persist the same partial shape, so an action-only change does not set `loginFormChanged` before separate profile revalidation runs.

### CAS protects profile writes, not the credential-release decision

**Confirmed:** discovery, approval, stale marking, and verification use `updateMany` conditions based on fingerprint and `updatedAt`, with retries where discovery/stale transitions can collide. The three credential-bearing paths load app plus relation, run a synchronous predicate, then separately read/decrypt the credential. A revalidation can change the profile to `STALE` between those operations; the already-loaded relation remains eligible and release proceeds.

A shared `authorizeBoundProfileLaunch()` should execute a conditional database operation immediately before each credential read. It must require the current detector version, `APPROVED`, non-`STALE`, equal current/approved/app-bound fingerprints, and saved-configuration match. A failed conditional operation must return the existing profile-review response; a success must bind release to the observed profile version.

### Verification writes exceed the authoritative binding boundary

**Confirmed:** the JSON branch treats only 2xx as transport validation and maps 401/403 to `REJECTED` (`app/api/portal-apps/verify-login/route.ts:268-283`). The persistence gate is narrower than the fingerprint: `matchesSavedAppConfiguration()` compares no `extraFields` names and no `jsonApi` contract, although both can change the request. A caller can test a different allowed contract or payload while retaining URL path/mode/method/field names, then record a profile state for the bound fingerprint.

**Confirmed:** `verificationUpdate` is outside `matchesSavedConfig`, so an unsaved/mismatched test updates `loginVerifiedAt` or `loginVerifyError` on the stored app. Construct an explicit non-secret verification snapshot from the saved app and bound profile—using selected canonical API contract and extra-field name set—and make profile and app writes conditional on that snapshot and current binding. Exploratory tests can still be reported in audit/UI without mutating trusted state.

### Profile `lastError` reintroduces an unredacted storage channel

**Confirmed:** discovery evidence is reduced to fixed structural messages and the migration clears legacy prose. The verification path bypasses that boundary: an unknown JSON contract embeds submitted `jsonApi.path` plus `apiProbe.note`, `persistVerificationResult()` forwards the result for a matched app, and `recordLoginProfileVerification()` persists it in `lastError` after only `.slice(0, 500)`. A `jsonApi.path` such as `/?redirect=<opaque-value>` satisfies the leading-slash schema check, so query-bearing request metadata can remain in the profile and later reach the UI.

Persist a safe outcome code such as `API_CONTRACT_NOT_FOUND`, `HTTP_DENIED`, or `FORM_REJECTED`; render localized text from that code. Keep full dispatch text transient in the HTTP response or audit only after its own redaction policy, never in profile/evidence.

### The hash self-check does not exercise the release boundary

**Confirmed:** `npx tsx scripts/test-fingerprint.ts` proves the standalone v2 hash changes for final/action/mode/method/contracts and ignores URL query/fragment. It does not construct a profile-bound POST relay, run a stale transition between guard and decrypt, submit a mismatched verification request, or assert `lastError` has no query/cookie-derived content. `npm run lint`, `npx tsc --noEmit`, `npx prisma validate`, and `git diff --check main` pass, but cannot detect these behavioral failures.
