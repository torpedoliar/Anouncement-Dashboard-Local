## 00 — Overview Portal Web SSO + Audit Trail
- source: docs/specs/00-overview.md
- type: protocol
- content:
  - Status: SPEC (belum diimplementasi) · Versi 3.0.0-draft · schemaVersion 9 · 2026-07-22.
  - Adds three capabilities to the multi-tenant announcement CMS without removing existing functions: (1) Portal Web SSO — separate login, RBAC-filtered app grid, SSO via user-stored credentials; (2) Portal RBAC — portal users fully separate from admin CMS users; (3) comprehensive Audit Trail — single source of truth for all transactions (admin CMS, portal user, system) with outcome, IP, device, redacted sensitive fields.
  - Keputusan utama D1–D8 (spec-internal decision table, NOT standalone ADRs): D1 portal users separate from CMS users (PortalUser vs User); D2 SSO via form-based credential forwarding; D3 credentials encrypted AES-256-GCM per (user, app); D4 new single AuditLog table (not reuse of ActivityLog — ActivityLog.userId NOT NULL cannot record system/portal events); D5 ActivityLog retained + backfilled; D6 no new dependencies (node:crypto, bcryptjs, next-auth, Prisma, Zod only); D7 portal managed by SuperAdmin CMS via /admin panel; D8 SSO mode FORM first, PortalSsoMode enum extensible (REDIRECT/PROXY/TOKEN future).
  - In-scope: models PortalUser, PortalApp, PortalUserAppAccess, PortalUserAppCredential, PortalSession, AuditLog + enums; portal auth (separate NextAuth, cookie prefix `portal-auth.*`, DB revocation, lockout, forgot/change password); portal RBAC + admin pages; form-based SSO (encrypted storage, auto-submit form, health indicator, failure UX, CSRF via extraFields); audit helper lib/audit.ts + retrofit of all mutation routes + unified admin page + export + retention + backfill; infra (env, docker-compose, seed, scripts, version bump, docs).
  - Out-of-scope (future): SSO modes REDIRECT/PROXY/TOKEN (OIDC/OAuth2/SAML); PORTAL_ADMIN delegation without SuperAdmin; portal email notifications; app health probes; portal self-registration.
  - Design principles: don't break existing; strict separation (portal session ≠ admin session, portal user ≠ admin user, new audit ≠ old); convention consistency (`@/lib/...`, getServerSession, Zod+validateInput, validatePagination, inline-style dark UI, Indonesian strings); security by default; audit never fails the main transaction (logAudit try/catch non-blocking); no new dependencies; extensible enums.

## 02 — Authentication & Sessions (Portal)
- source: docs/specs/02-authentication-and-sessions.md
- type: protocol
- content:
  - Separate NextAuth instance (lib/portal-auth.ts) for portal users; portal session ≠ CMS session; pattern follows lib/auth.ts (JWT + DB-backed revocation).
  - CredentialsProvider validates PortalUser: email found → isActive → lockedUntil → bcryptjs compare. Login failures logAudit LOGIN_FAILED (actorType=PORTAL_USER, outcome=FAILURE).
  - Cookie prefix `portal-auth.*` (sessionToken, callbackUrl, csrfToken): httpOnly, sameSite lax, path /. Route handler app/api/portal-auth/[...nextauth]/route.ts. pages.signIn "/portal-login"; session strategy "jwt", maxAge 12*60*60; secret reuses NEXTAUTH_SECRET.
  - Lockout: MAX_FAILED_ATTEMPTS = 5, LOCKOUT_DURATION_MS = 15 * 60 * 1000 (15 min); on 5th failure reset failedLoginCount=0 + set lockedUntil; audit ACCOUNT_LOCKED (category SECURITY, outcome FAILURE); reset on successful login; works together with per-IP middleware rate limit (08-security).
  - Forgot password: reset token (UUID) stored as resetTokenHash + resetTokenExpiresAt on PortalUser; email via lib/email.ts; audit PASSWORD_RESET_REQUESTED / PASSWORD_RESET_COMPLETED (category AUTH). Change own password at /portal/settings: verify old via compare, hash new via bcrypt.hash(password, 10); audit PORTAL_PASSWORD_CHANGE. Admin reset at /admin/portal-users: audit ADMIN_RESET_PORTAL_PASSWORD (actorType ADMIN_USER).
  - Session management: helpers getPortalSession / revokePortalSession / getPortalUserSessions in lib/portal-access.ts; API /api/portal-sessions GET (SuperAdmin all / PORTAL_USER own; validatePagination) and DELETE (revoke; audit PORTAL_SESSION_REVOKED, category AUTH); admin page /admin/portal-sessions mirrors /admin/sessions.
  - Env: PORTAL_CREDENTIAL_KEY (MANDATORY, 64-char hex / 32 bytes); AUDIT_RETENTION_DAYS (default 365, 0 = forever); PORTAL_SESSION_MAX_AGE (default 43200 s = 12 h). Fail-closed env validation at startup: invalid/missing PORTAL_CREDENTIAL_KEY → app throws.
  - types/next-auth.d.ts: session.user = { id, role: string, isSuperAdmin?, ...DefaultSession["user"] } — shared by both NextAuth instances; role stays string, guards do specific checks.
  - CMS vs portal comparison: users vs portal_users; user_sessions vs portal_sessions; next-auth.* vs portal-auth.* cookies; /admin-login vs /portal-login; redirect /admin vs /portal; maxAge 24 h vs 12 h; no lockout vs lockout 5×/15 min; isSuperAdmin boolean vs role===PORTAL_ADMIN (future).

## 03 — RBAC (Role-Based Access Control)
- source: docs/specs/03-rbac.md
- type: nfr
- content:
  - Three-layer model: Layer 1 SuperAdmin CMS (User.isSuperAdmin=true; full /admin, manage PortalApp/PortalUser/PortalUserAppAccess/PortalSession/AuditTrail + CMS); Layer 2 PORTAL_ADMIN (PortalUser.role — FUTURE; currently behaves as PORTAL_USER); Layer 3 PORTAL_USER (login, own grid per access, SSO launch, own credential CRUD, own sessions).
  - Admin panel matrix: portal management (/admin/portal-apps, /admin/portal-users, /admin/portal-sessions, /admin/audit-trail, sites/users mgmt) is SuperAdmin-only; ADMIN/EDITOR/VIEWER get no portal menu items (isSuperAdmin ? [...] : [] in AdminSidebar).
  - Portal matrix: grid = assigned only (PORTAL_USER); SSO launch only if access; credentials own-only; PORTAL_ADMIN future = all apps bypass.
  - Per-app access rules: row in PortalUserAppAccess → app in grid + SSO allowed; no row → not shown, SSO launch 403; PortalApp.isActive=false → hidden for everyone; PortalUser.isActive=false → login denied; PortalUser.role=PORTAL_ADMIN (future) → bypass access check.
  - Access vs Credential separation principle: Access (PortalUserAppAccess) admin-managed, unencrypted, UI /admin/portal-users, audit ACCESS_GRANTED/ACCESS_REVOKED; Credential (PortalUserAppCredential) user-managed, AES-256-GCM, UI /portal/credentials, audit CREDENTIAL_SAVED/CREDENTIAL_DELETED. Admin never sees plaintext credentials.
  - Helper signatures (lib/portal-access.ts): canAccessPortalApp(portalUserId, appId), canAccessPortalAppBySlug(portalUserId, appSlug), getAccessiblePortalApps(portalUserId), hasCredential(portalUserId, appId).
  - Portal layout guard: app/portal/layout.tsx server component uses getServerSession(portalAuthOptions), redirects /portal-login when unauthenticated; dark inline UI (#0a0a0a bg, #fff text), PortalHeader.
  - Zod schemas (lib/validation-schemas.ts): PortalUserCreateSchema (email ≤255, password 8–100, name 2–100 sanitized, role enum default PORTAL_USER, isActive default true, appIds optional); PortalUserUpdateSchema = partial omit password; PortalAppCreateSchema (slug regex, url/loginUrl must be valid URL, ssoMode enum default FORM, httpMethod POST|GET default POST, usernameField/passwordField 1–100 default username/password, extraFields any nullable, displayOrder int ≥0); PortalAppUpdateSchema = partial; PortalCredentialSchema (appId cuid, username 1–255, password 1–500, extra optional record).
  - RBAC audit events: ACCESS_GRANTED, ACCESS_REVOKED, PORTAL_USER_CREATED/_UPDATED/_DELETED/_ACTIVATED/_DEACTIVATED (USER_MGMT, ADMIN_USER), PORTAL_APP_CREATED/_UPDATED/_DELETED (PORTAL, ADMIN_USER).

## 04 — SSO Credential Forwarding
- source: docs/specs/04-sso-credential-forwarding.md
- type: protocol
- content:
  - File lib/portal-crypto.ts using node:crypto (no new deps). getKey() validates PORTAL_CREDENTIAL_KEY against /^[0-9a-f]{64}$/i, throws otherwise. encrypt/decrypt AES-256-GCM: random 12-byte IV, 16-byte auth tag, blob = base64(iv + tag + ciphertext); decrypt throws on tag mismatch. CredentialData { username, password, extra? } with encryptCredential/decryptCredential JSON wrappers. Plaintext exists in memory only during SSO launch; API credential never returns plaintext.
  - SSO launch flow (GET /portal/app/[appSlug], server component): 1 getServerSession(portalAuthOptions), redirect /portal-login if not logged in; 2 canAccessPortalAppBySlug → 403 AccessDenied; 3 findUnique credential (portalUserId, appId) → NoCredential prompt with link /portal/credentials?app=[slug]; 4 decryptCredential, on failure CorruptCredential ("Kredensial rusak, silakan simpan ulang"); 5 render auto-submit form (method=app.httpMethod, action=app.loginUrl, target=_blank, hidden usernameField/passwordField + extraFields) with body onLoad="document.forms[0].submit()"; 6 update lastUsedAt; 7 logAudit SSO_LAUNCH (category SECURITY, outcome SUCCESS). App inactive → notFound(). export const dynamic = "force-dynamic".
  - extraFields CSRF handling: type "static" (fixed token) in MVP; type "fetch" (server-side extraction from app login page) = future; type "fixed" for company/tenant fields. Example: `[{"name":"csrf_token","type":"static","value":"fixed-abc123"}]`.
  - Failure UX table: not logged in → redirect; no access → AccessDenied + back to /portal; no credential → "Anda belum menyimpan kredensial" + link; corrupt credential → re-save link; inactive app → 404; app-side submit failure → app shows its own error.
  - Known limit of FORM mode: portal cannot detect login outcome (cross-origin, no callback); health indicator (hasCredential per app in /portal grid, left-join optimization) is best-effort.
  - SSO modes: FORM = MVP; REDIRECT/PROXY/TOKEN = future. lib/portal-crypto.ts stays relevant for all modes.
  - Credential self-service API: POST /api/portal/credentials { appId, username, password, extra? } — portal session + canAccessPortalApp, encrypt → upsert credentialBlob, audit CREDENTIAL_SAVED; DELETE /api/portal/credentials?appId=[cuid] — owner check, audit CREDENTIAL_DELETED; GET /api/portal/credentials → [{ appId, appName, appSlug, hasCredential, lastUsedAt }], no plaintext.

## 08 — Security
- source: docs/specs/08-security.md
- type: nfr
- content:
  - Threat model (threat → mitigation): app credential theft from DB → AES-256-GCM at-rest, separate env key; memory dump → decrypt only at SSO launch, no plaintext cache; expose to client → credential API never returns plaintext; portal brute-force → lockout 5×/15 min + rate limit 10 req/min per IP; session hijacking → httpOnly + sameSite=lax + DB-backed revocation per refresh; privilege escalation → separate session cookies + separate guards; RBAC bypass → canAccessPortalApp on every route, server-side checks; XSS in audit changes → changes stored as JSON stringify, rendered as <code>; audit manipulation → no DELETE API for audit, retention only via scheduler; credential tampering → AES-GCM auth tag, decrypt throws; env key leak → .env gitignored, never logged, format validated at startup.
  - AES-256-GCM summary: key 32 bytes from PORTAL_CREDENTIAL_KEY (^[0-9a-f]{64}$); IV 12-byte random per encrypt; auth tag 16 bytes; blob base64(iv[12] + tag[16] + ciphertext); key rotation = re-encrypt all blobs (future scripts/rotate-portal-key.ts).
  - Redaction: SENSITIVE_KEYS = [password, passwordHash, credentialBlob, token, secret, sessionToken, resetToken, smtpPass]; recursive, case-insensitive; example: changes { email, password, name } → password = "[REDACTED]".
  - Lockout: 5 consecutive failures → 15 min; reset on success; audit ACCOUNT_LOCKED (SECURITY/FAILURE); two layers with rate limit (account-level lockout + per-IP middleware).
  - Rate limiting (existing middleware in-memory Map): default 300 req/min per (IP + path segment); auth (/auth, /login) 10 req/min; NEW /portal-auth, /portal-login 10 req/min; backup 5 req/min; in-memory resets on restart, not distributed, Redis future (single Docker container today).
  - Startup env validation (instrumentation.ts, Next 15, runs before requests): PORTAL_CREDENTIAL_KEY missing or not /^[0-9a-f]{64}$/i → throw FATAL (fail-closed); generate via openssl rand -hex 32.
  - Cross-origin limitations (FORM mode): sameSite=Lax usually OK for POST navigation, SameSite=Strict may fail, None;Secure needs HTTPS — portal cannot control, document requirement to apps; login outcome undetectable (no callback) — health indicator best-effort; CSRF tokens via extraFields (static MVP, fetch future); form POST navigation not subject to CORS.
  - Password policy: min 8, max 100, bcrypt.hash(password, 10), consistent with CMS UserCreateSchema; future complexity enforcement via Zod regex.
  - Security checklist (pre-deploy): PORTAL_CREDENTIAL_KEY set in .env + docker-compose; .env gitignored; instrumentation fail-closed; lockout 5×/15 min tested; rate-limit 10/min tested; portal-auth.* cookie prefix verified; /portal/* guard redirect; /admin/portal-* + /admin/audit-trail 403 non-SuperAdmin; credential API no plaintext; redact works; no AuditLog DELETE API; backup includes portal+audit tables; HTTPS production; strong NEXTAUTH_SECRET.
  - Compliance: retention 365/0; credentials encrypted at-rest, decrypted only at launch; IP/UA stored for forensics (future IP hashing); right to erasure = delete PortalUser cascades credential+session, AuditLog kept (SetNull + denormalized); CSV/JSON export for compliance.

## Portal App: Deteksi Otomatis Field Login (username/password) — Design
- source: docs/superpowers/specs/2026-08-12-portal-app-login-field-detection.md
- type: api-contract
- content:
  - Feature: "Deteksi Otomatis" button beside LOGIN URL in /admin/portal-apps add/edit form; server fetches loginUrl, parses HTML, auto-fills usernameField, passwordField, extraFields; admin reviews and saves.
  - Current-state anchors (from code): admin form fields loginUrl / usernameField (default "username") / passwordField (default "password") / extraFields (JSON textarea); PortalAppCreate/UpdateSchema (loginUrl z.string().url(), username/passwordField z.string().max(100).default, extraFields z.any().nullable()); PortalApp.extraFields Json — format Record<string,string>; SSO launch parses app.extraFields as Record<string,string> + cred.extra → array {name,value} injected into hidden form fields in SSOAutoSubmit; lib/portal-crypto.ts CredentialData { username, password, extra?: Record<string,string> }.
  - API: POST /api/portal-apps/detect-fields body { url } → { usernameField, passwordField, extraFields } — usernameField/passwordField = input NAME values (fallback id); extraFields = static hidden inputs with non-empty name+value as object Record<string,string> ({ name: value }) — object, NOT array, consistent with DB format.
  - Detection rules within a <form> containing a password input: username candidate from text|email|tel|search inputs — priority (1) autocomplete="username", (2) name/id lowercase containing user/login/email/account, (3) first non-password input; null → manual. Password = first type="password" input. Extra fields = all <input type="hidden"> (and untyped inputs defaulting hidden) with name+value non-empty; csrf_token/_token/authenticity_token detected (per-session values; admin may delete).
  - Limitations: parses static HTML only (no JS execution) — JS-rendered login forms fall back to manual; session/cookie-dependent login pages (e.g., Oracle REROUTE / AppsLocalLogin.jsp) may redirect to external SSO → null/failed; detection never opens credentials; dynamic per-session extra values may be useless stored.
  - Security (SSRF & URL validation): API SuperAdmin only (getServerSession(authOptions) + isSuperAdmin); URL http/https only; allowlist blocks localhost, 127.0.0.0/8, 0.0.0.0, 10/8, 172.16/12, 192.168/16, 169.254/16 (link-local); fetch(url, { redirect: "follow", signal: AbortSignal.timeout(8000) }); cap response body ~64KB before parse (prefer res.body reader abort); errors never leak HTML content (short message only).
  - Files: create app/api/portal-apps/detect-fields/route.ts; lib/portal-login-detect.ts pure function detectLoginFields(html) → { usernameField: string|null, passwordField: string|null, extraFields: Record<string,string> }; scripts/test-login-detect.ts self-check parser (variations: autocomplete, email vs text, hidden csrf, no form, multiple forms); modify app/admin/portal-apps/page.tsx (button + handler + preview + autofill). YAGNI: no auto-trigger on typing; no detection from app url (loginUrl only); no visual rendering of detected fields; no full-JS app support; no persistence of detection results.
